# Ask Compass architecture

This document describes what is deployed today and the target architecture for
customer workspaces. Anything marked **Target** is a design, not running code.

## 1. Three layers

| Layer | Domain | Purpose | Status |
|---|---|---|---|
| Marketing site | `askcompass.in` → `www.askcompass.in` | Explain the product, platform, solutions, resources, contact | **Live** |
| Public demo | `studio.askcompass.in/studio` (`demo.askcompass.in` and `www.askcompass.in/studio` redirect here) | No-login Studio with synthetic sample procedures | **Live** |
| Central app entry | `app.askcompass.in` | Workspace discovery, then sign-in. The header **Login** button on every page links here | **Placeholder** page at `/workspace`; no sign-in yet |
| Customer workspaces | `{company}.askcompass.in` | One organization's procedures, users and data | **Target**; unknown subdomains show “workspace not available” |

## 2. What is deployed today

- **Stack:** static HTML/CSS/JS generated by `apps/web/build.mjs` (Node, no dependencies), hosted on Vercel.
  The Vercel project uses Root Directory `apps/web`, build command `node build.mjs` and output `public/`.
- **Content:** `apps/web/src/content/*.mjs` (copy and capability status), `apps/web/src/sections/*.html` (homepage sections).
- **Studio demo:** `apps/web/studio.html` with `assets/js/studio.js`. All data lives in the visitor's browser (localStorage).
  Roles are a demonstration switch. There is no backend, database, authentication or shared state.
- **Legacy prototype:** `apps/web/app.html` (Build Compass, Workflow Engine, Dashboard, FAQ, Contact), kept unchanged.
  Old links such as `/#build` are redirected there by a small script on the homepage.
- **No secrets:** the repository contains no API keys, and no environment variables are required.

## 3. Hostname routing

Defined in `apps/web/vercel.json`. Redirects are evaluated before the filesystem, so they only apply to the
hostnames listed; `www.askcompass.in` is explicitly excluded and the marketing homepage never redirects.

| Request | Result |
|---|---|
| `www.askcompass.in/studio`, `/studio.html` | 307 → `https://studio.askcompass.in/studio` (the `#` route is kept by the browser) |
| `demo.askcompass.in/*` | 307 → `https://studio.askcompass.in/studio` |
| `studio.askcompass.in/` | 307 → `/studio` |
| `studio.askcompass.in/{other page}` | 307 → the same path on `www.askcompass.in` (Studio assets excepted) |
| `ceo.askcompass.in/` | 307 → `/ceo`, the leadership sign-in page (sign-in not live; nothing is sent or stored) |
| `www.askcompass.in/ceo` | 307 → `https://ceo.askcompass.in/ceo` |
| `ceo.askcompass.in/{other page}` | 307 → the same path on `www.askcompass.in` |
| `app.askcompass.in/` | 307 → `/workspace` |
| `{anything-else}.askcompass.in/*` | 307 → `/workspace/unavailable` (except `/workspace/unavailable` and `/assets/*`) |
| `www.askcompass.in/*` | Served normally |

These rules do nothing until the domains are added to the Vercel project (section 7).

When customer workspaces exist, the tenant rule must be replaced by **server-side tenant resolution**
(Vercel Routing Middleware or the application server): resolve the subdomain to a tenant record, check its status,
then serve the app. A static redirect is only a placeholder; a subdomain is never a security boundary on its own.

## 4. Target: multi-tenant data model

One shared application serves every organization. Every tenant-owned row carries `tenant_id`.
Proposed on PostgreSQL (for example Supabase, which the repository has used before; it is not configured now).

```
tenants            (id, slug unique, name, status: active|suspended|pending, branding jsonb, created_at)
users              (id = auth user id, email, name, created_at)
memberships        (tenant_id → tenants, user_id → users, role: owner|admin|approver|editor|viewer, unique(tenant_id, user_id))
invitations        (id, tenant_id, email, role, token_hash, expires_at, accepted_at)
procedures         (id, tenant_id, folder, title, owner_user_id, live_version_id, created_at)
procedure_versions (id, tenant_id, procedure_id, number, definition jsonb, status: draft|submitted|rejected|published|archived,
                    created_by, submitted_at, reviewed_by, review_comment, published_at)
executions         (id, tenant_id, procedure_version_id, user_id, path jsonb, status, started_at, completed_at)
feedback           (id, tenant_id, procedure_version_id, node_id, user_id, text, created_at)
audit_events       (id, tenant_id, actor_user_id, action, target_type, target_id, detail jsonb, created_at)
```

`definition jsonb` holds the same `{ start, nodes, edges }` shape Studio uses today, so guided runs and process maps
keep reading one definition. Index every table on `(tenant_id, …)`; enforce foreign keys within the same tenant.

### Isolation rules

1. Row-level security on every tenant table: a row is visible only if
   `exists (select 1 from memberships m where m.tenant_id = row.tenant_id and m.user_id = auth.uid())`.
   Write policies additionally check the role (editors write drafts, approvers publish, admins manage members).
2. The server derives the tenant from the **hostname** and the **authenticated session**, never from a
   tenant id sent by the browser. Requests for tenant A from a user without membership in A return 404.
3. Suspended or pending tenants resolve to the “workspace not available” page; no tenant data is read.
4. Publishing, rejecting, restoring and membership changes write an `audit_events` row in the same transaction.
5. Tests must cover: unauthenticated access, wrong role, cross-tenant reads and writes, forged tenant ids,
   unknown and suspended slugs, and that server-only keys never reach the browser.

## 5. Target: authentication and sessions

- Sign-in on `app.askcompass.in` (email + password or magic link, password reset, invitations), then redirect to the
  user's workspace. Later: SSO (SAML/OIDC) and MFA per tenant.
- Session cookie scoped to the workspace host (`{company}.askcompass.in`), `Secure`, `HttpOnly`, `SameSite=Lax`,
  with short expiry and server-side revocation. If a cross-subdomain cookie on `.askcompass.in` is used for
  convenience, every request must still verify membership for the requested tenant.
- Logout clears the session server-side.

## 6. Rollout phases

1. **Done:** marketing site, platform and solution pages, Studio demo, legacy prototype, host routing placeholders.
2. **Next:** provision a database project and server runtime; add `.env.example` with required variables
   (database URL, anon key for the browser, service key for the server only).
3. Tenants, users, memberships and invitations with RLS and the isolation tests above.
4. Move Studio's procedures, versions, approvals and audit log onto the server for signed-in workspaces;
   keep the public demo on synthetic browser data.
5. Executions and analytics events; notifications by email.
6. SI drafting and source-grounded answers (requires a model provider key, server-side only), always with human review.
7. Integrations and automation, each listed as available only after it is built and tested.
8. SSO, MFA, custom domains per enterprise tenant.

## 7. Manual steps (DNS and Vercel)

These cannot be done from the repository. DNS for `askcompass.in` is at GoDaddy.

1. In Vercel → Project → Domains, add the subdomain and connect it to Production.
2. In GoDaddy → askcompass.in → DNS, add a CNAME with the short name (for example `app`) and the value Vercel
   shows (currently `2d11c36d229eb95f.vercel-dns-017.com`). Leave the `@` A record and the `www` CNAME as they are.
3. Click Refresh in Vercel until the domain shows Valid Configuration; HTTPS is issued automatically.

Connected so far: `app`, `demo`, `studio`, `ceo` and `mithilajodi`. `ceo` shows the leadership sign-in page,
whose sign-in is switched off until real authentication exists; it takes no password or email. `mithilajodi`
(the first customer workspace) shows "workspace not available" until sign-in, tenant data and server-side
role checks exist. Nothing private is served on either.

For many customer workspaces, a wildcard `*.askcompass.in` is simpler. Vercel issues wildcard certificates only
when the domain uses Vercel's nameservers, so either move DNS to Vercel or keep adding each subdomain individually.
Keep Vercel Deployment Protection off for production so the public site and demo stay reachable.
